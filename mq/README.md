# Segmentation-Service MQ Layer

Этот модуль предоставляет инфраструктуру очередей для сервиса сегментации.
Он полностью изолирован: достаточно Docker + Python.

## Схема логики работы

### Графическая схема

![Segmentation Service Architecture](docs/sxem.png)

### Поток данных:

1. **API Service** принимает файлы от пользователя и сохраняет их в **File Storage**
2. API отправляет задачу в **RabbitMQ** (очередь `upload_tasks`)
3. **Math Worker** получает задачу из очереди и передает данные в **Math Service**
4. **Math Service** выполняет вычисления и возвращает результаты
5. **Math Worker** создает уникальный JSON-файл с результатами и отправляет путь к файлу в очередь `db_tasks`
6. **DB Worker** получает путь к файлу результатов, обрабатывает его и сохраняет данные в **Database**
7. Пользователь может запросить статус задачи через **API Service**


Внешний API → Celery.send_task("tasks.calculate", [folder_name, user_id]) → 
RabbitMQ → Math Worker → HTTP POST /run_process → process_survey() → 
результат → DB Worker

### Очереди и маршрутизация:

- `math_tasks`: задачи для обработки в Math Worker (задача `tasks.calculate`)
- `db_tasks`: задачи для сохранения результатов в DB Worker (задача `tasks.parse_and_store`)

### Конкурентность и параллельная обработка:

#### Ограничение параллельности:

- **Math Worker** обрабатывает задачи с ограничением параллельности (не более 3 одновременных задач)
- **DB Worker** может обрабатывать несколько задач параллельно (настраивается через `DB_WORKER_CONCURRENCY`)

#### Архитектура обработки файлов:

- **Math Worker** создает уникальный JSON-файл для каждого результата в директории `/app/data/results/`
- **DB Worker** читает файлы результатов и сохраняет данные в отдельные JSON-файлы для каждого пользователя в `/app/data/db/`
- Блокировки файлов не требуются, так как каждый процесс работает с уникальными файлами

#### Рекомендации по распределению CPU:

- **Оптимальное распределение**: использовать не более 80% доступного CPU, оставляя 20% для системных процессов
- **Распределение между воркерами**:
  - Math Worker: 60% от доступных ресурсов CPU (48% от общего CPU)
  - DB Worker: 40% от доступных ресурсов CPU (32% от общего CPU)

#### Реализация в Docker:

- Использовать `--cpus` или `--cpu-quota` для ограничения CPU в Docker Compose:

```yaml
services:
  math_worker:
    # ... другие настройки
    deploy:
      resources:
        limits:
          cpus: '0.48'  # 48% от общего CPU

  db_worker:
    # ... другие настройки
    deploy:
      resources:
        limits:
          cpus: '0.32'  # 32% от общего CPU
```

- В Celery используется `--concurrency` для ограничения количества параллельных задач

#### Настройка через переменные окружения:

Распределение ресурсов настраивается через переменные окружения в файле `.env`:

```bash
# Настройки распределения ресурсов
TOTAL_CPU_ALLOCATION=0.8  # общее выделение CPU (80% от доступного)
MATH_WORKER_CPU_SHARE=0.6  # доля Math Worker (60% от выделенного)
DB_WORKER_CPU_SHARE=0.4  # доля DB Worker (40% от выделенного)
MATH_WORKER_CONCURRENCY=3  # количество параллельных задач для Math Worker
DB_WORKER_CONCURRENCY=2  # количество параллельных задач для DB Worker
```

#### Текущие настройки распределения ресурсов:

- **Math Worker**: 48% от общего CPU (0.8 * 0.6), до 3 параллельных задач
- **DB Worker**: 32% от общего CPU (0.8 * 0.4), 2 параллельные задачи
- **Системные процессы**: 20% от общего CPU

## Текущая реализация и заглушки

Текущая реализация представляет собой прототип с заглушками для демонстрации работы очередей и конкурентного выполнения задач.

### Заглушки и имитация в текущем прототипе:

1. **Math Worker** (`workers/math_worker/tasks.py`):
   - Задача `calculate` имитирует длительные вычисления с помощью `time.sleep(5)`
   - Создает уникальный JSON-файл с результатами в директории `/app/data/results/`
   - Возвращает фиктивный результат с фиксированным значением `score=42.0` и путем к файлу результатов

2. **DB Worker** (`workers/db/tasks.py`):
   - Задача `parse_and_store` получает путь к файлу результатов от Math Worker
   - Обрабатывает файл результатов и сохраняет данные в отдельный JSON-файл для каждого пользователя в директории `/app/data/db/`

### Полная реальная реализация:

В реальной реализации сервиса сегментации будет использоваться следующий поток данных:

1. **FastAPI сервис** принимает DICOM-файлы от пользователей через API-эндпойнты

2. Загруженные файлы сохраняются в файловое хранилище, и задачи отправляются в очередь RabbitMQ

3. **Math Worker**:
   - Получает задачи из очереди с путями к DICOM-файлам
   - Передает файлы в сервис сегментации для обработки
   - Получает результаты сегментации и сохраняет их в JSON-файлы
   - Отправляет путь к файлу результата в очередь для DB Worker

4. **DB Worker**:
   - Получает путь к файлу результата
   - Парсит JSON-данные и сохраняет их в PostgreSQL
   - Обновляет статус задачи в базе данных

5. **API сервис** предоставляет эндпойнты для проверки статуса задач и получения результатов

## Автоматическая маршрутизация задач

В проекте реализована автоматическая маршрутизация задач на основе их имен:

- Задача `tasks.calculate` автоматически направляется в очередь `math_tasks`
- Задача `tasks.parse_and_store` автоматически направляется в очередь `db_tasks`

Это позволяет отправлять задачи без явного указания очереди:

```python
# Задача будет автоматически направлена в очередь math_tasks
result = app.send_task("tasks.calculate", args=[payload])

# Задача будет автоматически направлена в очередь db_tasks
db_result = app.send_task("tasks.parse_and_store", args=[output])
```

Маршрутизация настроена в файле `workers/celery_app.py` с помощью параметра `task_routes`.

## Архитектура

- **RabbitMQ**: Брокер сообщений
- **math_worker**: Воркер для математических вычислений, слушает очереди `math_tasks` и `celery`
- **db_worker**: Воркер для операций с базой данных, слушает очереди `db_tasks` и `celery`
- **Flower**: Веб-интерфейс для мониторинга Celery

## Важные замечания по использованию

1. **Отправка задач**: Задачи автоматически маршрутизируются в нужные очереди по их имени:
   ```python
   # Пример отправки задачи (автоматически попадет в очередь math_tasks)
   app.send_task('tasks.calculate', args=[payload])
   
   # Пример отправки задачи (автоматически попадет в очередь db_tasks)
   app.send_task('tasks.parse_and_store', args=[result])
   ```
   
   Маршрутизация настроена в `workers/celery_app.py` с помощью `task_routes`
